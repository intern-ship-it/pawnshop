# WhatsApp Gateway — Outbound Send API (integration spec for an external tenant app)

> Audience: an engineer (or AI agent) integrating a **server-side** application with
> the Grasp WhatsApp Gateway as a new tenant. This document describes **what exists
> today**, verified against the gateway source. Gaps are listed explicitly in §7 —
> do not assume anything not stated here.

**Base URL:** `https://wbapi.graspsoftwaresolution.com`
All routes are mounted under `/api`.

The gateway is a Node/Express + Prisma service that owns *all* AiSensy calls,
templates, broadcasts, wallet and billing. It is **multi-tenant by column**: every
row carries a `temple_id`. There is no database per tenant.

Message flow: `your app -> gateway -> AiSensy -> Meta -> WhatsApp`.
Your app must never call AiSensy directly.

---

## 0. TL;DR — the only endpoint most integrations need

```
POST https://wbapi.graspsoftwaresolution.com/api/internal/send
X-Service-Key: <SERVICE_API_KEY>
Content-Type: application/json

{ "temple_id":"...", "to":"...", "template":"...", "params":[...], "reference":"..." }
```

Everything under `/api/internal/*` is machine-to-machine (shared service key).
Everything else (`/api/send`, `/api/whatsapp/*`, `/api/templates`, `/api/projects/*`)
requires a **dashboard admin JWT** and is NOT usable by an external server app.

## 1. Onboarding a tenant

### 1.1 How a tenant is created

Three paths exist. **None is self-service over the service-key API.**

| Path | Endpoint | Auth | Effect |
|---|---|---|---|
| Onboard a new AiSensy account into an unclaimed **pool** | `POST /api/whatsapp/onboard` | admin JWT | Creates AiSensy business + project; stores an **unclaimed** pool row. Not bound to a tenant. |
| **Connect** an existing AiSensy project to a tenant | `POST /api/whatsapp/projects/connect` | admin JWT | Body carries `templeId` explicitly. Verifies AiSensy credentials by minting a real JWT *before* persisting, then creates the tenant's `Project` + `wallet` + `billing`. |
| Tenant binds itself to an account | `POST /api/internal/temple/connection` | **service key** + `X-Temple-ID` | Modes: `PARTNER` (claim pool row by id), `LINK` (claim by AiSensy project id), `DIRECT` (supply own AiSensy email + password). |

Read the current binding:

```
GET /api/internal/temple/connection
X-Service-Key: <SERVICE_API_KEY>
X-Temple-ID: <TEMPLE_ID>
```

Response:

```json
{ "success": true, "data": {
  "configured": true, "id": "...", "connection_mode": "PARTNER",
  "project_id": "...", "business_id": "...", "name": "...",
  "phone_number": "...", "status": "LIVE",
  "verification_status": "VERIFIED", "has_credentials": true }}
```

`{"configured": false}` means the tenant has no live project — every send will fail
with `409` until onboarding completes.

### 1.2 What identifies a tenant

**A free-form `temple_id` string** (e.g. `"temple1"`, `"ssv"`). It is not a UUID and
is not generated by any endpoint — it is assigned by convention and first exists when
a `Project` row is created carrying that value.

It is passed **two different ways depending on the endpoint** — this trips people up:

- **In the JSON body** as `temple_id` — `/internal/send`, `/internal/notify`,
  `/internal/broadcast`, `/internal/broadcast/quote`
- **As the `X-Temple-ID` header** — `/internal/templates`, `/internal/wallet`,
  `/internal/notifications`, `/internal/temple/connection`, `/internal/status`

(The header-reading helper also falls back to `body.temple_id` or `?temple_id=`, but
rely on the documented form per endpoint.)

### 1.3 The credential — READ THIS

**There is no per-tenant credential. There is exactly ONE global shared secret:
`SERVICE_API_KEY`**, held in the gateway's `.env` and compared as a plain string.

Implications you must design around:

- Your app receives the *same* secret that the temple backend and the cron worker use.
- Anyone holding it may pass **any** `temple_id` and send as **any** tenant. There is
  no binding between key and tenant, and no authorization check beyond the key itself.
- Rotating it breaks every caller simultaneously.
- There is **no issuance endpoint and no UI** that displays or mints it. It is handed
  over out-of-band as an environment variable.

It is not an API key per app, not a bearer token, not OAuth. Store it as a secret and
never expose it to a browser.

## 2. Send a TEXT message

### 2.1 Endpoint and auth

```
POST https://wbapi.graspsoftwaresolution.com/api/internal/send
X-Service-Key: <SERVICE_API_KEY>
Content-Type: application/json
```

Header name is exactly `X-Service-Key`, **raw value, no `Bearer` prefix**.
No `Authorization` header. No `X-Temple-ID` header — the tenant comes from the body.

This path is **synchronous**: the gateway calls AiSensy inside your request and
returns the real result (~300 ms typical).

### 2.2 Request body

| Field | Type | Required | Default | Notes |
|---|---|---|---|---|
| `temple_id` | string, min 1 | **yes** | — | tenant key |
| `to` | string, min 6 | **yes** | — | full international number, digits. See 2.3. |
| `template` | string, min 1 | **yes** | — | template **name** |
| `reference` | string, min 1 | **yes** | — | your idempotency key. See §6. |
| `language` | string | no | `"en"` | template language code |
| `category` | `MARKETING`\|`UTILITY`\|`AUTHENTICATION` | no | `"UTILITY"` | affects **pricing only** |
| `params` | string[] | no | `[]` | ordered `{{n}}` values. See 2.4. |
| `name` | string \| null | no | `null` | recipient display name; stored on the message row, **not** substituted into params on this endpoint |
| `buttons` | array | no | — | Meta button components, passed through unvalidated. See 2.6. |
| `document` | `{url, filename?}` | no | — | PDF header. See §3. |

Unknown extra fields are ignored.

### 2.3 Phone number format

Send the full international number in digits, e.g. `60123456789`, `919994001122`.
**No normalization is applied** — the string is forwarded to AiSensy as-is.

The country prefix is used to pick the billing rate:
`91`→IN, `971`→AE, `60`→MY, `65`→SG, `1`→US, `44`→GB, anything else → fallback rate.

### 2.4 Template selection and parameters

**Template is chosen BY NAME**, as a plain string. Not by id, not by key, not by
campaign, and no prior assignment or registration is required. Whatever you put in
`template` is sent straight to Meta.

**Parameters are an ORDERED ARRAY** — the same positional model as AiSensy's
`templateParams`. `params[0]` fills `{{1}}`, `params[1]` fills `{{2}}`, and so on.
Internally it becomes Meta's body component:

```json
{ "type": "body", "parameters": [{ "type": "text", "text": "..." }] }
```

Example — template `donation_success_notification` whose approved body is
`Dear {{1}}, your donation of {{2}} (receipt {{3}}) is {{4}}.`

```json
"params": ["Ravi Kumar", "MYR 250.00", "RCP-10231", "confirmed"]
```

Named/keyed parameters are **NOT supported on this endpoint**. A named form
(`variables` + a stored slot map) exists only on `/api/internal/notify`, which sends
by pre-configured *event* rather than by template name — see §5.

`{name}` / `{number}` placeholder substitution is **NOT applied** on
`/internal/send`; params are forwarded verbatim. That substitution applies only to
broadcasts and the admin send page.

### 2.5 CRITICAL: no template validation on this endpoint

`/internal/send` does **not** check that the template exists, is `APPROVED`, or that
your param count matches the template's `{{n}}` count. Sequence on mismatch:

1. Wallet is charged.
2. Meta rejects (`132000` = param count mismatch, `131008` = empty param).
3. Gateway refunds and returns `502`.

So: **validate your param count yourself** against `GET /api/internal/templates`
(§4.2), and never send an empty-string parameter — Meta rejects blanks as hard as a
count mismatch.

(The APPROVED + count checks do exist, but only on the admin-JWT route `/api/send`,
which your app cannot use.)

### 2.6 Buttons (optional)

For templates with dynamic buttons (e.g. an OTP URL button). Passed to Meta as-is and
not validated by the gateway:

```json
"buttons": [
  { "type": "button", "sub_type": "url", "index": 0,
    "parameters": [{ "type": "text", "text": "483920" }] }
]
```

`index` is the button's zero-based position in the APPROVED template. Omitting this
for a button template renders an empty button that taps through to nothing.

### 2.7 Success response — HTTP 200

```json
{
  "success": true,
  "data": {
    "status": "SENT",
    "provider_message_id": "wamid.HBgLNjAxMjM0NTY3ODkVAgARGBI5...",
    "charged": "0.0530",
    "currency": "MYR"
  }
}
```

- `data.provider_message_id` is **the message id**. Store it — delivery webhooks are
  matched back by this value. It may be `null` if AiSensy returned no id.
- `charged` is in `currency` (the tenant's wallet currency), `0` when billing is off.

Also HTTP 200 — **idempotent replay** (same `reference` already succeeded):

```json
{ "success": true, "data": { "status": "ALREADY_SENT", "reference": "...", "charged": 0 } }
```

Treat `ALREADY_SENT` as success. Note it carries **no** `provider_message_id`.

### 2.8 Failure responses

| HTTP | Body | Meaning | Retry? |
|---|---|---|---|
| `401` | `{"success":false,"message":"Invalid service key."}` | bad/missing `X-Service-Key` | no |
| `422` | `{"success":false,"errors":{"to":["String must contain at least 6 character(s)"]}}` | validation failure — **`errors` is a field-keyed object, not a string** | no |
| `409` | `{"success":false,"message":"Temple 'x' has no WhatsApp project connected yet."}` | tenant not onboarded, or project has no stored credentials | no |
| `402` | `{"success":false,"message":"Insufficient WhatsApp balance: 0.0000 MYR available, 0.0530 MYR required. Please top up."}` | wallet empty | after top-up |
| `502` | `{"success":false,"message":"AiSensy sendMessage failed (HTTP 400): {...}","data":{"status":"FAILED","refunded":"0.0530"}}` | AiSensy/Meta rejected the send. Wallet **auto-refunded**, `reference` **released** | yes, same reference |
| `404` | `{"success":false,"message":"Not found."}` | unknown `/api/*` path | no |
| `500` | `{"success":false,"message":"..."}` | unhandled server error | with backoff |

**Error field naming is inconsistent** — parse defensively:
`message` (a string) on every failure **except** `422`, which returns `errors` (an
object of field → array of messages).

## 3. Send a DOCUMENT / PDF

**Same endpoint, same auth, same body**, plus one optional field:

```json
"document": { "url": "https://your-app.example.com/receipts/10231.pdf",
              "filename": "receipt.pdf" }
```

- `url` — **required** if `document` is present; must be a valid absolute URL.
- `filename` — optional, defaults to `"document.pdf"`. This is the name the recipient
  sees in WhatsApp.

It becomes Meta's document header component:

```json
{ "type": "header",
  "parameters": [{ "type": "document", "document": { "link": "...", "filename": "..." }}]}
```

Auth, template-by-name, ordered `params`, response shapes and status codes are
**identical to §2**.

### 3.1 Public URL required — base64 is NOT accepted

The file is sent to Meta as a `link`. **Meta's servers fetch it**, so the URL must be:

- publicly reachable from the internet,
- served **without** authentication, cookies or IP restriction,
- fast — a slow, generated-on-the-fly PDF can time out and fail the send,
- correct `Content-Type` (`application/pdf`).

There is **no base64 upload on any send path.** (The gateway does have a base64
intake, but it is admin-JWT-only and exists solely to attach a *sample* file when
*creating* a template for Meta approval — it cannot be used to send.)

### 3.2 Constraints

- The template must have been **APPROVED with a DOCUMENT header**. Sending a document
  to a plain template — or a document-header template with no document — fails with
  Meta error **132012**.
- `/internal/send` supports **document only**. It cannot send image or video headers.
  (The gateway core supports all three, but only `/internal/notify` exposes them.)
- If the send fails, the gateway refunds and returns `502`. There is **no** automatic
  fallback to a plain text template on this endpoint.

## 4. Templates

### 4.1 Do templates need to be assigned to a tenant?

**For `/internal/send`: no.** Pass the template name directly. Nothing links a
template to a tenant inside the gateway — the template merely has to exist and be
APPROVED on that tenant's AiSensy project.

**For `/internal/notify` (event-based sending): yes, mandatory** — see §5.

### 4.2 Listing a tenant's templates

```
GET https://wbapi.graspsoftwaresolution.com/api/internal/templates
X-Service-Key: <SERVICE_API_KEY>
X-Temple-ID: <TEMPLE_ID>
```

Returns only APPROVED templates, read **live from AiSensy** (not a stale local cache):

```json
{ "success": true, "data": [
  { "name": "donation_success_notification",
    "category": "UTILITY",
    "language": "en",
    "body": "Dear {{1}}, your donation of {{2}} (receipt {{3}}) is {{4}}.",
    "variable_count": 4 }
]}
```

Two behaviours to guard against:

1. **It is best-effort.** Any failure — bad credentials, AiSensy down, tenant not
   onboarded — returns **HTTP 200 with `data: []`**, never an error. An empty list
   does *not* mean "this tenant has no templates". Do not treat `[]` as authoritative.
2. `variable_count` is the **highest `{{n}}` index** found in the body — which is
   exactly the length your `params` array must have.

**Not available here:** there is no `has_doc_header` flag, so over the service-key API
you cannot discover which templates accept a PDF. You must know that out-of-band.

### 4.3 Creating templates

Not possible over the service-key API. Template creation/deletion is admin-JWT only
(`POST /api/templates`, `POST /api/whatsapp/projects/:id/templates`). New templates
must be requested from Grasp and approved by Meta before use.

## 5. Event-based sending (`/internal/notify`) — usually NOT what you want

```
POST /api/internal/notify
X-Service-Key: <SERVICE_API_KEY>
```

Sends by a **pre-configured event key** rather than a template name, and supports
**named** variables plus image/document/video headers. Use it only if Grasp has
configured your event; otherwise use `/internal/send`.

Body: `temple_id`, `to`, `event`, `reference` (all required), plus optionally
`name`, `params` (positional), `variables` (named object), `receipt_pdf_url`,
`media` `{type: image|document|video, url, filename?}`, `buttons`.

Why it is usually unsuitable for an external app:

- **Event keys are a fixed compile-time catalog** in the gateway's source
  (`donation_success`, `pledge_overdue`, `pledge_reminder`, `pos_success`,
  `product_donation_success`, `pooja_booking`, `hall_booking`, `ubayam`,
  `member_registration`, `prasadam`, `rental_reminder`, `daily_closing`, …).
  **You cannot register a new event over the API** — it requires a code change and a
  redeploy.
- **Double gate.** A notification sends only when BOTH are true:
  `allowed` (set by Grasp staff, admin JWT) AND `enabled` (set by the tenant).
  Grasp also assigns `templateName`, `receiptTemplateName` and the `paramMap`
  (slot → variable-name ordering). The tenant cannot pick templates.
- **A closed gate returns HTTP 200 with `status: "SKIPPED"`** — a success-shaped
  response for a message that was never sent:

  ```json
  { "success": true, "data": { "status":"SKIPPED", "event":"...",
      "reason":"not allowed or not enabled for this temple" }}
  ```

  Always inspect `data.status`; never treat HTTP 200 alone as "delivered".

Its advantages over `/internal/send`, if configured: named `variables` resolved via
the stored `paramMap`, automatic param count reconciliation, image/video headers, a
CC fan-out list, and an automatic fallback to a plain template when a media send fails.

## 6. Idempotency, retries and limits

### 6.1 `reference` is the idempotency key — get this right

`reference` is required on `/internal/send` and `/internal/notify`. The wallet debit is
keyed on it with a UNIQUE constraint.

- A retry with the **same** `reference` after a success returns `ALREADY_SENT`:
  no second charge, no second message.
- On failure the gateway refunds **and releases** the reference, so retrying a `502`
  with the same reference genuinely re-sends.
- Use a stable, business-meaningful key: `"myapp:donation:10231"`,
  `"otp:60123456789:1721394000"`. Never a random UUID per attempt — that defeats it.
- This is what makes a timed-out request safe to retry.

### 6.2 What the gateway does NOT do

- **No rate limiting.** No throttle, no quota, no `429` anywhere in the gateway.
- **No IP allowlisting.** The shared service key is the only gate.
- **No automatic retry** on `/internal/send` — one attempt, then `502`. Retrying is
  your responsibility (use the same `reference`, add exponential backoff).

(The gateway's internal broadcast worker does retry up to 3 attempts per recipient,
but that applies only to queued broadcasts, not to `/internal/send`.)

### 6.3 What you must respect

| Constraint | Value |
|---|---|
| Request body size limit | **2 MB** |
| Upstream AiSensy timeout | **30 s** — set your client timeout above this (35–40 s) |
| Wallet balance | send refused with `402` when the tenant cannot afford it |
| CORS | restricted to the dashboard origin — a **browser cannot call this API**; server-side only |

Meta-level realities that are not gateway bugs:

- Error **131049** ("healthy ecosystem engagement") is Meta's **marketing frequency
  cap**, not a fault in your request. The charge is auto-refunded.
- Marketing templates are rate-limited by Meta per recipient. Use `UTILITY` for
  transactional messages.

### 6.4 Bulk sending

Do **not** loop `/internal/send` over hundreds of recipients — that is one synchronous
AiSensy round-trip per person inside a single request and will time out mid-list.

Use instead:

```
POST /api/internal/broadcast
X-Service-Key: <SERVICE_API_KEY>

{ "temple_id":"...", "template":"...", "language":"en", "category":"MARKETING",
  "params":["{name}", "shared value"],
  "recipients":[ {"to":"60123456789","name":"Ravi"},
                 {"to":"60198765432","name":"Meena","params":["Meena","custom"]} ] }
```

Returns immediately with `{ "broadcast_id", "queued", "charged", "currency" }`.
Nothing is sent inside the request — a **cron worker** drains the queue, so delivery
begins within about a minute. In broadcast `params`, `{name}` and `{number}` **are**
substituted per recipient; per-recipient `params` override the shared array.

Price a batch without charging: `POST /api/internal/broadcast/quote`
with `{temple_id, numbers[], category}` → `{count, unit_price, cost, balance,
balance_after, currency, billing_enabled, affordable}`.

Broadcasts move **only if the gateway's cron drain is running**. `/internal/send`
is synchronous and does not depend on it.

## 7. GAPS — what does not exist. Design around these.

1. **No per-tenant credential.** One global `SERVICE_API_KEY` for every caller, with
   no key↔tenant binding and no per-tenant authorization. Your app can send as any
   tenant; rotating the key breaks all callers at once.
2. **No rate limiting, no quotas, no IP allowlist, no `429`.** The only backpressure
   is the wallet balance.
3. **No self-service tenant onboarding.** Creating a tenant needs a dashboard admin
   JWT or a pre-existing pool entry. There is no "register a tenant" service-key
   endpoint, and `temple_id` values are assigned by convention, not generated.
4. **`/internal/send` performs no template validation** — no existence, APPROVED, or
   param-count check. Validate client-side or pay for messages Meta rejects.
5. **Document sends require a public, unauthenticated URL.** No base64 on any send path.
6. **`/internal/send` cannot send image or video headers** — document only.
7. **Template listing fails silently**, returning `200 []` instead of an error.
8. **No way to discover which templates accept a PDF** over the service-key API.
9. **Inconsistent error shape**: `message` (string) on most failures, `errors`
   (object) on `422`.
10. **No template creation** over the service-key API.
11. **Cannot add new notification events** without a gateway code change and redeploy.

### Suggested client logic

```
1.  Once per tenant at startup: GET /api/internal/templates -> cache name -> variable_count.
    Treat an empty list as "unknown", not as "none".
2.  Before each send: assert params.length === variable_count for that template,
    and that no param is an empty/whitespace string.
3.  POST /api/internal/send with a deterministic `reference` derived from your
    business entity (e.g. "myapp:invoice:10231").
4.  Client timeout 35-40 s (upstream AiSensy timeout is 30 s).
5.  On 200: check data.status.
      "SENT"          -> store data.provider_message_id
      "ALREADY_SENT"  -> treat as success (no message id is returned)
      "SKIPPED"       -> /internal/notify only; the event gate is closed
6.  On 502 or 500: retry with the SAME `reference`, exponential backoff, cap attempts.
    On 402: stop and alert - the tenant's wallet needs a top-up.
    On 401/409/422: do not retry - it is a configuration or payload bug.
7.  For >50 recipients: use POST /api/internal/broadcast, not a loop.
```
